# Skills Whitelist

Hermes ships many built-in skills. Each **enabled** skill injects its own
description into the system prompt. Enabling everything bloats the prompt,
wastes context window space, and slows inference on a local model.

This document explains two strategies for keeping the skill set tight, and
recommends an approach for this scaffold.

---

## Strategy A — Include-list (whitelist) — recommended for this scaffold

Decide the small set of skills your roles actually need, then **disable
everything else**.

Because Hermes config exposes `skills.disabled` (a deny-list), an include-list
is implemented as:

```
deny-list  =  (all available skills)  −  (your include-list)
```

### How to build yours

1. List all skills available in your hermes install:
   ```bash
   python -m hermes_cli.main skills list
   # or whichever CLI subcommand your version exposes
   ```

2. Define your include-list (the skills you actually need):
   ```python
   INCLUDE = [
       "file",
       "terminal",
       "kanban",
       "memory",
       "web",
       "code_execution",
       "browser",
   ]
   ```

3. Generate the deny-list = all skills not in INCLUDE, and paste it under
   `skills.disabled` in `config/config.yaml.example` (base) and in each
   profile overlay that needs a further narrowed set.

4. After each hermes version upgrade, regenerate the deny-list — new skills
   added upstream will otherwise silently enter the prompt.

### Per-role guidance

| Role | Skills to INCLUDE | Skills to EXCLUDE (examples) |
|---|---|---|
| **orchestrator** | kanban, cronjob, memory, messaging, clarify | code_execution, lsp, browser, web/search |
| **coder** | file, terminal, code_execution, lsp, memory, kanban, clarify | browser, art, social, messaging |
| **planner** | web, kanban, memory, clarify | code_execution, lsp, browser, art |
| **qa-tester** | browser, terminal, code_execution, memory, kanban, clarify | lsp, web/search, art, social |

These are starting points — adjust to the skills your version of hermes actually
ships. Profile overlays can narrow further: for example, qa-tester should
disable file-mutation skills even if the base config includes `file`.

## Strategy B — Deny-list

An alternative approach is a large **explicit deny-list** in `config.yaml`
rather than a computed whitelist. This list contains entries for skills the
workflow never needs (art generation, social media, media conversion, etc.).

This approach works well when you know your environment well, but has a
maintenance gap: **new hermes versions add skills** and a deny-list silently
lets new skills through, growing the prompt over time.

### `.skills_prompt_snapshot.json`

Hermes generates an auto-generated `.skills_prompt_snapshot.json` in
`${HERMES_HOME}`. This file is a cached snapshot of the effective skills
system-prompt so hermes does not recompute it on every gateway startup.

- It is **auto-generated by hermes** on first run (or when skills change).
- Do **not** hand-edit it.
- Delete it to force regeneration (e.g. after changing `skills.disabled` or
  adding new skills to `skills.external_dirs`).
- Do **not** commit it — add it to `.gitignore` alongside `config.yaml` and
  `state.db`.

---

## Custom skill directories

`skills.external_dirs` in `config.yaml` accepts a list of absolute paths to
directories containing additional skill files. Example:

```yaml
skills:
  external_dirs:
    - /path/to/your-project/hermes/skills
```

The scaffold leaves this empty with a placeholder. Add your own skill directory
here after setting up `$HERMES_HOME`.

---

## Why the include-list scales better for adopters

| | Include-list (A) | Deny-list (B) |
|---|---|---|
| **New hermes skills** | Blocked by default — safe | Silently allowed — prompt grows |
| **Setup effort** | One-time generation step | Needs manual pruning each upgrade |
| **Prompt size** | Bounded by include-list | Grows with hermes releases |
| **Works with unfamiliar hermes versions** | Yes | Requires knowing all skill names |

**Recommendation:** start with an include-list (Strategy A), regenerate after
each hermes upgrade, and graduate to a known-good deny-list once your skill set
is stable.

## Applying the configuration

Edit `skills.disabled` in `config/config.yaml.example` for the base deny-list,
then layer per-profile narrows in each `config/profiles/<role>/config.yaml.example`.

```yaml
# config.yaml.example (base)
skills:
  disabled:
    - art-generation
    - social-media-post
    - <skill-to-disable-N>

# config/profiles/qa-tester/config.yaml.example (profile override)
skills:
  disabled:
    - art-generation
    - social-media-post
    - file-write       # qa-tester must not mutate source
    - file-delete
    - <skill-to-disable-N>
```

Keep the effective skill prompt small — prompt size directly affects token cost and reasoning bandwidth.
